# Pass 2 · Stage D plan — Generated-paper intake

**31 October 2026. Decisions taken (§11) and implementation approved the same day; §1–§10 are the plan as reviewed.** Stages A, B and C are built and
verified (D28–D30). This plan covers spec §3C's "papers that generate themselves" for the four
module sources: Materiality, Sampling, Analytical Review and WorkMind. Papers the Financial
Spine produces (lead schedules, the adjustment chain) are Stage E and only their *contract*
is fixed here.

## 1. What the specification requires, and nothing more

The spec's words on generated papers, in full:

| Where | Words |
|---|---|
| §3C | "A paper produced by a module arrives complete, with its inputs and its citations, and nobody retypes anything." |
| §3C Materiality | "The materiality memo, with the benchmark, the band and the figures from the spine" |
| §3C Sampling | "The sampling paper, **with the formula and the seed printed on it**" |
| §3C Analytical Review | "The variance paper, current year against prior, with the thresholds used" |
| §3C Financial Spine | "Every lead schedule, and the adjustment chain" (Stage E) |
| §3C WorkMind | "One paper per accepted run, carrying the run id, the inputs and the source-row citations" |
| §6 Pass 2 | "generated papers from Materiality, Sampling, Analytical Review and the Spine · … · WorkMind run papers" |
| §7 | "Automatic drafting of conclusions. That is WorkMind, and it is gated." |
| §8.8 | "A sampling paper generated by the Sampling module carries its formula and its seed." |
| §4 | No table or column for provenance; `wp_version.body` is the immutable record |

Everything else about these modules is **unknown**: the shape of a benchmark or a band, the
formula language, the seed type, what a threshold looks like, what "accepted" means for a
WorkMind run, how a source row is cited. None of those modules exists on `D:\` (`D:\CAF` holds
only the Financial Spine; its architecture D20 says "the materiality module (SA 320) does not
exist yet"). The Binder therefore **checks presence and shape of what the spec names, stores
the rest verbatim, and invents no semantics**. Where a rule needs a reading of the spec, it is
listed in §9 for decision, not assumed.

## 2. What exists today (inspected 31 Oct 2026)

- **Creation**: `POST /api/binders/{id}/papers` → `papers.create_paper` validates the nine
  content fields (`ref`, `section`, `title`, `sa_refs`, `objective`, `procedure`,
  `population_sample`, `result`, `conclusion`), refuses a reused reference, writes the `wp`
  row in `draft` with no version.
- **Versions**: `papers.prepare` snapshots the paper (`papers.snapshot`: the content fields plus
  the attachments by SHA-256) into `wp_version.body`, hashes it (`hashing.content_hash`:
  canonical JSON, SHA-256), writes version N with `prepared_by/at`. `review` and `sign_off`
  write N+1 and N+2 with the same hash, refusing if the content moved. Any content edit returns
  the paper to `draft`. `wp_version` is append-only at the database (migration 0001).
- **Sign-off rules**: no conclusion → no sign-off (8.1); open review note → no sign-off (8.2);
  every version records who and when (8.9).
- **Attachments**: belong to the paper from upload; join the signed record at the next prepare
  (D17); every version body lists them, so the hash covers the evidence.
- **Assembly/produce**: the manifest lists every paper with its current version's hash; the
  archive carries `paper.json`, every `versions/NNNN.json` (the whole body), notes,
  cross-references and native attachments. **Anything placed in a version body is therefore
  already hashed, frozen and exported.**
- **Identity**: `OAK_AUTH=dev|header`; `CurrentUser` is the acting person. There is no notion
  of a service identity yet.
- **Spine link** (D29): `binder.spine_version_id`; the Spine double in tests; locked versions
  carry `performance_materiality` and `pm_source`.

## 3. Design

### 3.1 One intake endpoint, one contract, per-source rules

`POST /api/binders/{binder_id}/generated-papers` (201 → `PaperOut`).

```jsonc
{
  "paper": {                       // exactly the fields a hand-made paper has (spec 3B)
    "ref": "C-1", "section": "C", "title": "Materiality memo", "sa_refs": ["SA 320"],
    "objective": "...", "procedure": "...", "population_sample": null,
    "result": "...", "conclusion": null
  },
  "generated": {
    "source": "materiality",       // materiality | sampling | analytical_review | workmind | spine
    "module": "oak_materiality",   // the producing module's name, free text
    "module_version": "1.4.0",     // optional
    "run_id": "…",                 // required for workmind (spec); see decision 7 for others
    "generated_at": "2026-10-31T10:00:00+05:30",
    "inputs": { ... },             // what the module computed from — stored verbatim
    "citations": [ ... ],          // where each figure came from — stored verbatim
    "materiality":        { "benchmark": ..., "band": ..., "spine_figures": { "version_id": "…", ... } },
    "sampling":           { "formula": "…", "seed": … },
    "analytical_review":  { "periods": { "current": "FY26", "prior": "FY25" }, "thresholds": ... },
    "workmind":           { "run": { "accepted_by": "…", "accepted_at": "…" }, "source_row_citations": [ ... ] }
  }
}
```

Only the block matching `source` is read; the others must be absent. `inputs` and
`citations` are required by §3C for every source ("arrives complete, with its inputs and its
citations") and are stored as given, bounded in size (decision 11).

### 3.2 Per-source rules the Binder enforces at intake (422 with the field named)

| Source | Required (from the spec's words) | Shape check only |
|---|---|---|
| all | `paper.ref/section/title`, `generated.source`, `module`, `generated_at`, `inputs` (non-empty), `citations` (non-empty list) | — |
| `materiality` | `benchmark`, `band`, `spine_figures` present and non-empty | `spine_figures.version_id` is a UUID; when the binder is linked it must equal the linked version (decision 5) |
| `sampling` | `formula` (non-empty text), `seed` (present; int or text) | both must appear verbatim in the paper's text so they are "printed on it" (decision 4) |
| `analytical_review` | `periods.current`, `periods.prior` (non-empty, different), `thresholds` (non-empty) | — |
| `workmind` | `run_id`, `inputs`, `source_row_citations` (non-empty list), the run **accepted** (decision 6) | each citation names a `source` and a `row` |
| `spine` | refused in Stage D: "Spine-produced papers arrive in Stage E" | — |

General refusals: binder not open (409; decision 9); reference already used (409, as today);
same `source` + `run_id` already received (409, "one paper per accepted run"; decision 7);
a `conclusion` on a WorkMind paper (422; §7: conclusions are not auto-drafted and WorkMind is
gated — decision 3 covers who writes it); provenance larger than the cap (413).

### 3.3 Where provenance lives: in every version body, from one append-only row

The version body is already the immutable, hashed, exported record, so **the `generated`
block is written into `body["generated"]` of every version** of the paper: the content hash
then covers the inputs and citations, and the archive carries them in `versions/NNNN.json`
without a new member. Because `snapshot()` reads the `wp` row, the provenance must be stored
with the paper so that later versions (review, sign-off, amendments) carry the same block.
Two ways (decision 2):

- **(a) Table `wp_generation`** — migration 0008: `id`, `wp_id`, `source`, `module`,
  `module_version`, `run_id`, `generated_at`, `received_by` (the acting identity),
  `received_at`, `payload` JSONB (the whole `generated` block), `content_hash_at_intake`;
  append-only trigger and SELECT/INSERT grants like every record table; CHECK `source IN (…)`;
  partial unique index on `(source, run_id)`. One row per intake, so Stage E's "regenerate as a
  new version" adds a row and the history stays whole. `snapshot()` embeds the latest row.
  **Recommended**: it follows the model's append-only pattern and §4's spirit.
- **(b) Columns on `wp`** — `generated_by` text and `provenance` JSONB, nullable; simpler,
  but regeneration overwrites the row's provenance (the old block survives only in old version
  bodies).

Either way migrations 0001–0007 are untouched and nothing changes for hand-made papers: their
bodies gain no key, so **every existing version hash and assembled file hash stays valid**.

### 3.4 Status on arrival and who prepares (decision 1)

- **(a) Arrives `draft` with provenance; a person prepares it.** The preparer's sign-off is
  then a real person attesting the module's output; 8.9's "user" is a user. "Nobody retypes
  anything" still holds because the content came in whole and (decision 3) cannot be retyped.
  **Recommended.**
- **(b) Arrives `prepared`, version 1 written at intake with the module as preparer.** The
  file shows the module as preparer; a reviewer and signer follow. Faster, but a module is
  named where SA 230 expects a person, and Stage F's review levels start from a preparer that
  cannot answer a review note.

### 3.5 Editability of a generated paper (decision 3)

"Nobody retypes anything" and §7 together suggest: the module's fields are **locked** (a
PATCH touching `objective`, `procedure`, `population_sample`, `result`, `title`, `section`,
`sa_refs` on a generated paper is refused with "regenerate from <module>"), while
**`conclusion` stays a person's** to write (§7). The version body records
`generated.content_hash_at_intake` over the module-supplied fields, so any divergence is
detectable for ever. Alternative: allow edits, mark the version "edited after generation".

### 3.6 Attachments arriving with the paper (decision 10)

Modules may send native files (a sampling workbook, a variance table). **(a)** multipart
intake: a `payload` JSON part plus `files[]`, stored through the existing attachment path
(SHA-256, vault, write-once) before any version is written; or **(b)** the module uploads
through `POST /api/papers/{id}/attachments` after intake, which joins the record at the next
prepare (D17) — fine under 3.4(a), not under 3.4(b).

### 3.7 Identity for module calls (decision 8)

Modules are servers. Under `OAK_AUTH=header` the proxy must supply an identity for them
(a service identity such as `sampling@oak`), recorded as `received_by`; `generated.module`
is recorded separately. Optional **`OAK_INTAKE_CREDENTIAL`**: a bearer the module must
present on this one endpoint, mirroring `OAK_SPINE_CREDENTIAL` on the other side. Not a new
auth system.

### 3.8 Screen and archive

- **Paper screen** (screen 2): a read-only "Generated" panel: source, module and version, run
  id, generated at, received by and when, then the source block (formula and seed; thresholds
  and periods; benchmark, band and Spine figures; run acceptance and citations), then
  `inputs` and `citations` as collapsible JSON. The edit form shows locked fields as such
  (decision 3). The Binder screen's index marks generated papers.
- **Archive**: no new member; `paper.json` gains `generated_by` (source) and the provenance is
  in every `versions/NNNN.json`. Acceptance 8.8 is then testable end to end: a generated
  sampling paper's produced archive carries its formula and its seed.
- **Access log, assembly, cross-references, Spine link**: unchanged.

## 11. Decisions taken — 31 October 2026

Approved after the conflict review against the specification. These govern the build.

| # | Decision |
|---|---|
| 1 | Generated papers arrive as **drafts**; a human preparer prepares and the chain signs off. The module is never `prepared_by`. |
| 2 | Provenance in an **append-only `wp_generation` table** (migration 0008), one row per intake; the block is embedded in every version body. |
| 3 | **Module-generated fields are locked** (title, section, SA references, objective, procedure, population and sample, result): a PATCH touching one is refused. The **conclusion stays human**. Materiality, Sampling and Analytical Review may supply a conclusion; a **WorkMind conclusion is refused** (spec §7). |
| 4 | A sampling paper's **formula and seed must appear verbatim in the paper's text** and in the provenance block. |
| 5 | Materiality **Spine figures are checked against the linked version** (mismatch refused). Unlinked binder: figures preserved, marked **not checked**. |
| 6 | **WorkMind intake is refused** until the module exists and accepted-run verification is possible. The contract is defined, validated and tested; the gate refuses after validation with a clear reason. |
| 7 | `run_id` **required for WorkMind, optional for the other three**; **unique per source** when supplied. |
| 8 | The authenticated identity is recorded as **`received_by`**; an optional **`OAK_INTAKE_CREDENTIAL`** bearer is required when set. |
| 9 | **No intake after assembly** (refused); regeneration of existing papers is Stage E. |
| 10 | **Supporting attachments are uploaded separately through the existing attachment API after intake creates the draft paper, but before the preparer completes preparation. The preparer must be able to review the generated content and its supporting attachments before proceeding.** (Clarified 31 Oct 2026 after the attachment-workflow investigation: an attachment row belongs to its paper, D17, so no file can attach before intake creates the paper; no staging table, migration 0009 or second attachment lifecycle is introduced.) Sequence: intake creates the draft → files are attached through `POST /api/papers/{id}/attachments` → the preparer reviews content and attachments together → prepare writes version 1 covering both. |
| 11 | `inputs` and `citations` **opaque, size-capped** (`OAK_MAX_PROVENANCE_BYTES`, default 1 MiB); the source blocks are **strict** (unknown keys refused). |
| 12 | Under `OAK_AUTH=header`, intake is open only to identities in **`OAK_INTAKE_IDENTITIES`**; none configured means no intake. In `dev` any identity may call. |

Spec words honoured and nothing added: the per-source fields are exactly §3C's; no shape is
assumed for a benchmark, band, threshold or citation beyond "present and non-empty".
